# 案例研究 3：构建多智能体诊断框架

#### 你将学到的内容

在本案例研究中，您将获得构建多智能体系统的实际操作经验，适用于高风险应用领域。具体而言，您将能够：

- 实现一个*医院诊断工作流程*，由规划器和执行者代理通过共享上下文进行通信。
- 将训练好的机器学习*分类器作为工具*整合到一个代理流程中。
- 用语言模型替换基于规则的规划器，并*评估*其对路由和诊断准确性的影响。
- 使用分类和路由指标评估系统性能，将规划器错误与执行器错误区分开来。
- 批判性地反思在医疗环境中部署主动系统的*局限性、风险和伦理*考量。

#### 14.1 场景概述

本案例研究侧重于构建和扩展一个简化的多智能体使用由模型上下文协议（MCP，第11章）启发的共享上下文的医院模拟[\[Hou et al.,](#page-5-0) [2026\]](#page-5-0)该案例研究旨在提供在高风险领域中使用自主架构的实践经验，重点强调协调、规划、评估和安全考虑。

您将模拟医院环境中的诊断工作流程。患者案例由代理处理，这些代理仅通过共享上下文进行交互：

- *规划代理* 决定应遵循哪个诊断路径。

{1}------------------------------------------------

- *执行者代理* 使用经过训练的机器学习分类器来生成诊断。
- *共享上下文* 存储案例、任务、中间决策和结果。

该模拟以离散步骤运行，并记录案件如何在系统中流动。与之前的案例研究一样，本案例的目标*不是*构建临床有效的系统，而是帮助你理解代理架构在高风险领域中的行为：代理如何通过共享状态进行协调，语言模型在分诊角色中的表现如何，以及此类系统的限制和安全问题出现的位置。<sup>1</sup>

##### 14.3.2 第一步：理解和运行基线

基线实现，`basic_mcp.py`，使用三个基于规则的规划代理，每个代理都硬编码为特定疾病。在运行任何程序之前，请仔细阅读代码。它实现了三个在本案例研究中反复出现的组件：

- 共享上下文（类似 MCP 的层）。一个中心数据结构，用于存储接收的患者案例、分配的诊断任务和诊断结果。所有代理仅通过这个共享上下文进行交互，永远不会直接相互作用，这反映了第 11 节中讨论的模型上下文协议的共享状态协调模式。
- 规划代理。每个基于规则的规划器读取未分配的案例，使用固定规则决定其疾病领域是否适用，并在共享上下文中创建任务。
- 执行器代理。每个执行器读取分配给其专业的任务，运行第 0 步中相应训练好的机器学习分类器，生成预测结果，并将结果写回共享上下文。

运行基线模拟，观察单个患者案例如何在系统中流动：从到达、通过计划和任务创建，到执行及结果记录。
  
 **分析问题：** 评估此基线设置有多贴近现实。性能评估得有多好？在处理患者和诊断的方式中存在哪些隐含假设？

##### 14.3.3 步骤 2：用 LLM 代理替换基于规则的规划器

在第二部分，`llm_mcp.py` 中，三个基于规则的规划器被一个基于 LLM 的规划器代理取代。这对于规划器来说是一个实质上更困难的任务：每个患者案例现在将来自*所有三个*数据集的特征组合成一个记录，并使用提供的 make case text 函数转换为文本描述，你不允许修改该函数。LLM 规划器必须读取这个组合的文本案例描述，并在没有硬编码规则的情况下决定哪些诊断路径适用。
  
 你的任务是：

{3}------------------------------------------------

- 实现一个函数，该函数调用真实的 LLM（例如，通过 Ollama 使用本地模型，或通过 OpenAI 或 Gemini API）以获取规划器对给定案例的决策；
- 实现 LLMPlannerAgent 的 step() 方法，使其为每个案例选择一个或多个诊断途径以及一个主要诊断；
- 优雅地处理格式不正确或无法解析的 LLM 输出，而不是因为一个错误的响应让模拟崩溃；并且
- 记录每一个规划器决策，以及作出该决策的案例，以便在运行后分析规划器的行为。

因为规划器现在必须从非结构化文本中推断相关性，而不是从固定规则中推断，所以这一步应该让你直接体验当一个 LLM 被置于决策角色时出现的可靠性问题：解析失败、不一致的格式，以及 LLM 的路由决策与数据集的真实标签之间的不一致。
  
 **交付成果：** 一个可运行的 `LLMPlannerAgent`、一份关于你使用了哪个 LLM 以及你如何访问它（本地 vs. API）的简短说明，以及完整模拟运行的记录的规划器决策。

#### 14.4 评估

你必须评估系统的两个组件，并保持这两个评估分开：

- 模型（执行者）性能：使用混淆矩阵和标准分类指标（准确率、精确率、召回率、F1）评估每种疾病的执行者预测。
- 规划器性能：使用路由决策的精确度和召回率（案例是否被发送到正确的疾病路径或路径？）以及主要诊断的准确性（规划器是否正确识别了主要问题？）来评估 LLM 的分诊质量。

在你的报告中，要清楚地区分由于错误路由（规划器错误）导致的错误和由于模型预测错误（执行者错误）导致的错误。一个案例可能独立地因为任一原因失败：一个路由正确的案例仍可能被执行者错误分类，而一个可正确分类的案例可能完全错过，因为规划器从未将其路由到正确的路径上。仅报告一个端到端的准确率数字会掩盖这种区别，这对于本案例研究是不够的。

#### A. 基线架构

- 用不超过五个句子描述单个患者案例在基线系统中的流程。
- 每个基线案例都是从数据集中抽取的，因此根据构建，它恰好属于一个疾病领域。这对基于规则的规划器的“决策”方式意味着什么，这是否是一个现实的分诊模型？
- 步骤0中的分类器是在用于生成模拟案例的相同数据分布上训练和评估的。为什么这种方法在方法论上存在问题，公平的评估方案会是什么样的？

#### B. LLM 规划设计

- 你使用了哪个 LLM，以及你是如何访问它的（本地模型、API）？请简要说明选择的理由。
- 案例文本生成功能将患者呈现为从三个独立、无关的数据集中提取的特征的组合。为什么这在医学上不现实，这对本练习的目的重要吗？
- 描述你在 step() 实现中的一个具体设计选择——例如，你如何处理解析失败、弃权，或被分配到多种疾病的情况——并解释你这样做的原因。

#### C. 结果

- 报告每种疾病的分诊精确率和召回率，以及执行模型的混淆矩阵。这些数字告诉你整体系统的工作效果如何？
- LLM 计划器可以同时将单个病例分配到多种疾病。给出一个这种做法有益的示例场景，以及一个可能有害的示例场景。

#### D. 反思

- 确定在医疗分诊环境中使用 LLM 作为规划器时特有的一项安全风险，并描述如何进行缓解。
- 通过将 LLM 的分流决策与原始单疾病数据集的真实标签进行比较来评估分诊性能，这样做公平吗？请说明您有的任何顾虑。

#### <span id="page-5-0"></span>可选扩展

作为一个额外的扩展，你可以通过使患者抽样更加真实来扩展系统（例如，使用更有原则的先验抽取混合或合并疾病的病例）。你还可以从UCI存储库中添加另一种疾病，或者引入一个评估者或验证者代理，在决策到达执行者之前检查规划器的决定。另一个想法是模拟人类参与的决策过程，或者引入不确定性阈值和弃答机制，以便在规划器不确定时可以拒绝分配病例。最后，你可以整合来自外部知识源的检索（第12章），使规划器能够在临床参考资料的基础上做出分配决策，而不只是依赖纯粹的参数化知识。

#### 笔记

本作业是教育性质的，非临床性质。请勿对在此构建的任何系统声称具有医疗有效性。重点在于清晰性、可重复性和批判性反思，而不是单纯的性能表现。在这种情况下，一个保守地进行路由、在不确定时选择弃答，并对其局限性保持透明的系统，其结果比最大化准确率但隐藏失败模式的系统更好。

#### 14.6 结论性意见

本案例研究汇集了本书早期部分的几个主题：代理角色与协调（第三部分）、工具使用与模型上下文协议（第11章），以及在复合代理系统中区分计划错误与执行错误所需的评估方法。通过首先构建基于规则的基线，然后用单一的基于 LLM 的规划器替换其规划器，你可以直接看到，一旦规划依赖于 LLM 对非结构化文本案例描述的解释而不是固定规则，规划变得多么困难。

医学框架是经过深思熟虑选择的：这是一个对过度自信、无法解释的错误成本很高的领域，同时放弃、人工监督和可审计性的问题是核心设计要求。相同的协调模式在医疗保健之外同样适用，适用于任何智能系统，其中语言模型负责路由决策，而其他更专业的组件随后执行这些决策。
