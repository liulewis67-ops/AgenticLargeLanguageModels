# 案例研究 3：构建多智能体诊断框架

#### 你将学到的内容

本案例以简化的医院诊断流程为背景，演示规划智能体、执行智能体与共享状态的协作方式。完成练习后，你将能够：

- 搭建由**规划智能体**和**执行智能体**组成的模拟诊断流程，并通过共享上下文协调任务。
- 将预先训练的机器学习**分类器作为工具**接入智能体工作流。
- 使用 LLM 规划器替换规则规划器，并评估对任务路由及预测结果的影响。
- 分别衡量路由与分类性能，区分规划错误和执行错误。
- 讨论医疗等高风险场景中的**适用边界、安全风险和伦理要求**。

## 14.1 场景概述

本案例构建一个简化的医院工作流模拟：多个智能体通过共享上下文交换任务与结果。这种设计受到模型上下文协议（MCP，第 11 章）相关思想的启发 [\[Hou et al.,](#page-5-0) [2026\]](#page-5-0)，但**共享状态数据结构并不等同于 MCP 协议本身**。练习的重点在于任务协调、规划决策、独立评估和安全边界。

模拟系统接收患者案例，并让不同职责的智能体只通过共享上下文传递信息：

- **规划智能体（Planner）**：决定应该执行哪些诊断路径。

{1}------------------------------------------------

- **执行智能体（Executor）**：调用已训练的分类器，生成对应的预测结果。
- **共享上下文（Shared Context）**：保存输入案例、任务分配、中间决策和结果。

模拟按离散步骤执行，并记录案例在系统中的流转过程。**本练习不用于临床诊断，也不能据此认定系统具备医疗有效性。** 它旨在帮助读者观察共享状态协调、LLM 分诊决策和错误传播等工程问题。<sup>1</sup>

## 14.3 实施步骤

### 14.3.1 步骤 0：训练诊断模型

- **糖尿病：** 皮马印第安人糖尿病数据集。
- **乳腺癌：** 威斯康星乳腺癌数据集，可通过 `sklearn.datasets` 获取。

- **心脏病：** UCI 心脏病数据集。

### 14.3.2 第一步：理解和运行基线

基线脚本 `basic_mcp.py` 包含三个基于规则的规划智能体，每个智能体只负责一种疾病。建议先阅读代码，明确以下三个组件及其职责：

- **共享上下文**：集中保存案例、已分配任务和预测结果。智能体通过读写共享数据协作，而不是互相直接通信。这是案例采用的协调方式，不是对 MCP 连接机制的完整实现。
- **规划智能体**：检查尚未分配的案例，通过固定规则判断是否属于其疾病领域，再向共享上下文写入任务。
- **执行智能体**：读取分配给自己的任务，调用步骤 0 中训练好的分类器，并写回预测结果。

运行基线模拟，跟踪一个案例如何经历**接收 → 路由 → 创建任务 → 分类预测 → 结果记录**的过程。
  
**分析问题：** 这种简化流程与真实医疗分诊有哪些差异？它采用了哪些隐含假设，又可能如何影响评估结果？

### 14.3.3 步骤 2：用 LLM 代理替换基于规则的规划器

在 `llm_mcp.py` 中，用一个 **LLM 规划智能体**替换原先三个基于规则的规划器。此时任务难度显著增加：每个模拟案例会拼合来自**三个独立数据集**的特征，再通过给定的 `make_case_text` 函数转换为文本（**不要修改该函数**）。模型必须从文本推断适用的诊断路径，而不能依靠原先的硬编码路由规则。
  
 你的任务是：

{3}------------------------------------------------

- 实现一个函数，该函数调用真实的 LLM（例如，通过 Ollama 使用本地模型，或通过 OpenAI 或 Gemini API）以获取规划器对给定案例的决策；
- 完成 `LLMPlannerAgent.step()`，为每个案例选择一个或多个诊断路径，并给出主要诊断路径；
- 对格式不符、无法解析或信息不足的输出提供明确的错误处理，不因单次无效响应使整个模拟中断；
- 记录每一个规划器决策，以及作出该决策的案例，以便在运行后分析规划器的行为。

这一步能直接暴露 LLM 承担决策职责时可能遇到的问题：输出格式不稳定、解析失败、路由选择与真实标签不一致，以及难以解释的判断。
  
 **交付成果：** 一个可运行的 `LLMPlannerAgent`、一份关于你使用了哪个 LLM 以及你如何访问它（本地 vs. API）的简短说明，以及完整模拟运行的记录的规划器决策。

## 14.4 评估

评估时必须**分别测量规划器与执行器**，不能只报告整个系统的单一准确率：

- **执行器分类性能**：针对每种疾病绘制混淆矩阵，并报告准确率、精确率、召回率和 F1。
- **规划器路由性能**：衡量每种诊断路径的精确率和召回率，检查案例是否分配给正确的执行器；另行统计主要诊断路径的准确率。

报告中要区分两类错误：**路由正确但分类错误**属于执行器问题；**本应执行某项分类却未被分派**则属于规划器问题。两者都可能使端到端结果失败，因此必须单独分析。

#### A. 基线架构

#### <span id="page-5-0"></span>可选扩展

作为一个额外的扩展，你可以通过使患者抽样更加真实来扩展系统（例如，使用更有原则的先验抽取混合或合并疾病的病例）。你还可以从UCI存储库中添加另一种疾病，或者引入一个评估者或验证者代理，在决策到达执行者之前检查规划器的决定。另一个想法是模拟人类参与的决策过程，或者引入不确定性阈值和弃答机制，以便在规划器不确定时可以拒绝分配病例。最后，你可以整合来自外部知识源的检索（第 12 章），使规划器能够在临床参考资料的基础上做出分配决策，而不只是依赖纯粹的参数化知识。

#### 笔记

**本作业仅用于教学与架构研究，不具有临床用途。** 不得把模拟结果视为医疗有效性证明。应优先保证实验可复现、错误可追踪，并在不确定时提供弃权和人工审核机制，而不是一味追求高准确率却掩盖失败模式。

## 14.6 结论性意见

本案例将前文介绍的**智能体分工、任务协调、工具调用与分项评估**结合在一个可运行的模拟流程中。通过比较规则规划器与 LLM 规划器，可以观察非结构化输入如何增加路由决策的不确定性。通过首先构建基于规则的基线，然后用单一的基于 LLM 的规划器替换其规划器，你可以直接看到，一旦规划依赖于 LLM 对非结构化文本案例描述的解释而不是固定规则，规划变得多么困难。

医学框架是经过深思熟虑选择的：这是一个对过度自信、无法解释的错误成本很高的领域，同时放弃、人工监督和可审计性的问题是核心设计要求。相同的协调模式在医疗保健之外同样适用，适用于任何智能系统，其中语言模型负责路由决策，而其他更专业的组件随后执行这些决策。
